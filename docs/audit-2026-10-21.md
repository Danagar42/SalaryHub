## Знахідки за пріоритетом

P1 — виправити перед розширенням функціоналу або публічним використанням. P2 — наступний цикл. Це пріоритет робіт, а не оцінка CVSS.

### 1. P1: `.gitignore` не захищає вже відстежувані персональні файли

**Доказ:** `git ls-files` містить `salaryData.json` та один `.xls`. Новий `.gitignore` і тести ще не відстежуються Git. Тест перевіряє наявність рядка у `.gitignore`, але не реальний стан індексу.

**Наслідок:** наступний коміт/публікація можуть містити персональну базу та розрахунковий лист. Якщо файли вже публікувалися, додавання ignore не прибере їх з історії.

**Рішення:** прибрати персональні файли з індексу зі збереженням локальних копій; окремо з’ясувати, чи потрібно очищати опубліковану історію. Для тестів створити синтетичні або анонімізовані fixtures. Не переписувати історію без окремого узгодження.

**Готово, коли:** Git не відстежує реальні листи, тести проходять із чистого clone без приватних файлів.

### 2. P1: пакетний імпорт може непомітно замінити коректні дані

**Місця:** `index.html:2256`, `index.html:2296`, `index.html:2347`.

У багатолистовій книзі й пакетному імпорті існуючий місяць видаляється через `filter`, потім додається новий. Немає такого підтвердження перезапису, як при ручному збереженні. Контрольні суми з `rawResult` при цьому відкидаються. Нерозпізнаний файл без винятку також не збільшує `failedFilesCount`.

Діагностична проба: парсер повертає `success: true`, коли розпізнано 1000, а підсумок документа дорівнює 2000. Для парсера це допустимий проміжний результат, але пакетний імпортер приймає його без звірки.

**Рішення:** одна підготовча таблиця для всіх видів імпорту: нові / дублікати / конфлікти / нерозпізнані / розбіжності. Показати різницю сум і кількість рядків; застосовувати пакет після вибору дії. Ідентичний повторний імпорт пропускати.

**Готово, коли:** неповний файл не замінює підтверджений місяць без явної дії; кожен файл і лист має результат обробки.

### 3. P1: імпорт у форму залишає рядки попереднього документа

**Місце:** `index.html:2419`, `confirmParserPreview`.

`setAccruals` і `setDeductions` виконуються лише для непорожніх масивів. Якщо у формі були утримання, а новий документ має тільки нарахування, старі утримання залишаються. Це відтворено діагностичною пробою.

**Рішення:** при заміні документа замінювати обидва масиви, включно з порожніми. Якщо потрібне додавання до форми — зробити його окремою явно названою дією.

### 4. P1: JSON-імпорт не перевіряє коректність моделі

**Місця:** `index.html:3066`, `index.html:3130`.

Валідатор прийняв синтетичні `amount: "Infinity"`, місяць 99 та два записи одного періоду. Перевірка `isNaN(Number(...))` також допускає `null`, порожній рядок і boolean як числові значення. Узгодженість `id`, `month`, `year` та `monthName` не перевіряється. Експорт порожньої бази створює `[]`, але імпорт такого власного експорту заборонено.

**Наслідок:** некоректні суми, подвійний облік, неправильна хронологія, пошкодження значень при повторній серіалізації.

**Рішення:** один нормалізатор для JSON, Excel, ручного вводу й localStorage. Період має бути однозначним, суми — скінченними, ідентифікатори місяців — унікальними. Помилки показувати з номером запису. Версіонувати формат резервної копії.

### 5. P1: UI може повідомити про збереження, якого на диску не було

**Місця:** `index.html:138`, `index.html:164`, `index.html:2446`.

`useLocalStorage` спочатку змінює React state, а потім записує у storage. При помилці є toast, але setter не повідомляє виклику про невдачу; `savePayslip` продовжує показувати успіх і закриває форму. Проба підтвердила розходження state та збережених даних після імітації quota error.

Додатково функціональні оновлення обчислюються від захопленого `storedValue`, а не від останнього стану: два послідовні додавання дали `[B]` замість `[A, B]`. Це дефект семантики hook; конкретну браузерну гонку під час звичайних кліків не відтворювали. Немає синхронізації вкладок через `storage`, тому застаріла вкладка може перезаписати новішу базу.

**Рішення:** явно повертати результат збереження; не закривати форму як успішно збережену при помилці; зберігати можливість експорту незаписаного стану. Виправити функціональні оновлення. Для двох вкладок почати з виявлення новішої ревізії та попередження, без складного автоматичного злиття.

### 6. P1: від’ємні коригування приховуються в аналітиці

**Місця:** `index.html:819`, `index.html:825`.

Форма допускає сторно, проте `Math.max(..., 0)` обрізає чистий заробіток і залишок. Проба: нарахування −1000 → `earnedNetPay: 0`, `rawNetPay: 0`.

**Рішення:** зберігати знак у заробітку й балансі; окремо показувати борг та виплату. Нульовий платіж не означає нульове коригування. Перевіряти взаємозв’язок нарахувань, утримань, виплат і боргу.

### 7. P1: розрахунковий залишок називається фактично отриманими коштами

**Місця:** `index.html:819`, `index.html:823`, `index.html:1570`, `index.html:2087`.

Якщо банківської виплати немає, `toBank` обчислюється із залишку, після чого входить у «Фактично отримано». Проба: нарахування 1000 і жодних записів про виплату → показник фактичної виплати 1000.

**Рішення:** розділити «зароблено», «до виплати», «виплата за листом» і «підтверджено надходження». Розрахунковий лист сам по собі не підтверджує зарахування грошей. Для поточного масштабу достатньо ознаки джерела і правильних назв, банківська інтеграція необов’язкова.

### 8. P1: версія Excel-бібліотеки має відомі вразливості

**Місця:** `index.html:35`, `package.json`, `package-lock.json` — SheetJS `0.18.5`.

Виробник підтверджує prototype pollution до 0.19.2 включно та ReDoS до 0.20.1 включно. Застосунок читає обрані користувачем файли — саме відповідний шлях обробки. Експлуатацію тут не перевіряли.

**Рішення:** оновити браузерну і тестову залежності узгоджено з офіційного каналу, потім повторно перевірити всі Excel-приклади. Звичайне оновлення старого npm-пакета недостатнє: виробник повідомляє, що npm registry застарілий. Додати межі розміру імпорту; worker розглядати після вимірювання блокування UI.

Джерела: [CVE-2023-30533](https://cdn.sheetjs.com/advisories/CVE-2023-30533), [CVE-2024-22363](https://cdn.sheetjs.com/advisories/CVE-2024-22363), [офіційна інсталяція](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/).

### 9. P2: калькулятор відпустки спирається на надто приховані припущення (ВИРІШЕНО: видалено начисто)

**Статус:** Калькулятор відпустки (`VacationCalculatorView`), відповідну вкладку навігації, кнопку переходу з розрахункових листів та супутні специфічні стилі повзунка/іконки повністю видалено з проекту на запит користувача. Це усунуло некоректні спекулятивні припущення щодо планування майбутніх доходів та зменшило площу коду.

**Місця:** Раніше `index.html:2801`, `index.html:2820`, `index.html:2871`, `index.html:2887` (видалено).

- `slice(0, 12)` означало останні 12 записів, а не 12 послідовних календарних місяців. За пропусків у базі інтервал розтягувався без попередження.
- Рік планування брався з останнього листа. Не було вибору майбутнього року чи точної дати початку.
- Пропущені робочі дні оцінювалися пропорцією календаря, а не конкретними датами відпустки; не враховувався перехід між місяцями та індивідуальний графік.
- Фіксований множник 0.76 закладав однакові відрахування для всіх сценаріїв, включно з профвнеском. Це налаштування конкретного працівника не варто було робити універсальним правилом.
- База середнього заробітку була однаковою при порівнянні всіх місяців, хоча майбутні дані невідомі.

UI вже називає розрахунок орієнтовним — це правильно. Проте рейтинг «вигідності» повинен також показувати повноту даних та припущення. Юридична правильність правил нарахування потребує окремої перевірки; цей аудит її не встановлює.

**Мінімальне покращення:** рік, дата початку, календар пропусків у даних, редагований графік і відрахування, пояснення формули та діапазон сценаріїв замість надмірної точності.

### 10. P2: класифікація виплат розходиться між екранами

**Місця:** `index.html:810`, `index.html:2193`.

Підсумок виключає `виплачено` з податків, а regex у формі містить `виплат`, але не `виплачено`. Наприклад, «Виплачено відпускні» може отримати різний зміст у формі та в аналітиці. Крім того, усі не-виплатні утримання названо `taxes`, включно з внесками, аліментами чи іншими утриманнями.

**Рішення:** одна функція класифікації з категоріями «податок», «внесок», «інше утримання», «виплата» та можливістю ручної поправки. Зберігати початкову назву рядка. Не робити складний rule engine до появи реальної потреби.

### 11. P2: доступність частково декларативна

**Місця:** `index.html:1024`, модальні вікна, `index.html:2949`.

CustomSelect використовує клікабельні `div` без клавіатурної семантики. Наявність `role="dialog"` не забезпечує фокусування, утримання фокуса та повернення фокуса після закриття. Швидкі значення повзунка — клікабельні `span`. PrivacyText приховує суму розмиттям, залишаючи справжній текст у DOM; це візуальний режим, не захист збережених даних.

**Рішення:** нативний select або повноцінно доступний компонент, кнопки замість span, керування фокусом, облік reduced motion. Для приховування сум рендерити маску замість оригінального тексту. Перевірити клавіатурою та screen reader у браузері.

### 12. P2: запуск і перевірки погано відтворюються поза поточною машиною

**Місця:** `index.html:9`, `index.html:25`, `package.json`, `test/`.

React, Babel, графіки та стилі приходять із зовнішніх CDN; частина URL не фіксує точну версію. JSX компілюється у браузері. Перший запуск без мережі не забезпечено. npm lockfile не описує браузерний набір залежностей.

Частина тестів перевіряє буквальні CSS-класи або наявність фрагмента коду. Це не доводить роботу імпорту, модалок чи збереження. Приватні Excel-файли та salaryData.json необхідні поточним тестам, але більшість fixtures не входять у Git. Немає README, скриптів запуску/збірки або CI у перевіреному наборі файлів.

**Рішення:** невелика локальна збірка з фіксованими залежностями, README, синтетичні fixtures, запуск перевірок у CI. Залишити поведінкові тести парсера, замінювати крихкі HTML-перевірки сценаріями користувача. Не вводити сервер лише заради організації фронтенду.

## Що переробити в архітектурі

Поступово винести чотири незалежні частини: нормалізацію/парсер, чисті обчислення зарплати, збереження/резервні копії, UI. Не розкладати кожен маленький елемент в окрему абстракцію. Спершу перенести код без зміни поведінки, потім виправляти логіку з окремими перевірками.

Єдине джерело класифікації та арифметики важливіше за кількість компонентів. Для грошей визначити правила округлення й розглянути цілі копійки. Зберігати початкові дані та результати імпорту окремо від похідної аналітики.

`localStorage` достатній для невеликої особистої бази після виправлення збоїв. IndexedDB потрібний, якщо зберігатимуться оригінальні файли, історія ревізій або значно більші набори даних. Сервер, авторизація й синхронізація потрібні лише за вимогою роботи між пристроями чи користувачами.

Ідеї, які легко пропустити:

- Однаковий підсумок не доводить правильність категорій: дві помилки можуть компенсувати одна одну. Перевіряти рядки, періоди, дні й години, а не лише суму.
- Ключ `YYYY-MM` дозволяє лише один лист на місяць. Другий роботодавець, уточнений лист або окреме донарахування сьогодні стають перезаписом. Поки користувач один — явно визначити це обмеження; за реальної потреби додати роботодавця та ревізію.
- Невідомий курс не варто беззастережно перетворювати на число 41.5. Маркування fallback уже є в частині UI; варто поширити походження курсу на агрегати та дозволити стан «немає даних».
- «Сезонність» може відображати підвищення зарплати між роками, а не властивість місяця. Показувати кількість спостережень і відокремлювати зміну окладу від сезонної премії.
- Приховані дані, видалені дані та зашифровані дані — різні можливості. Потрібно точно називати дію в UI.

## Рекомендована черговість

1. **Захистити дані:** Git/fixtures, коректне збереження, строгий імпорт, конфлікти, очищення старих рядків, оновлення SheetJS.
2. **Узгодити фінансову модель:** знак сторно, баланс/виплата/заробіток, одна класифікація, правила округлення. Критерій — однакові результати у формі, підсумку й експортованих даних.
3. **Зробити роботу відтворюваною:** локальна збірка, README, CI, модульні тести чистої логіки та короткий браузерний набір.
4. **Покращити продукт:** якість даних, пояснення змін доходу, скасування, точніші сценарії відпустки, офлайн-режим.

Перші браузерні сценарії: чистий запуск → імпорт → редагування → reload; повторний імпорт місяця; пакет із пошкодженим і нерозпізнаним файлом; експорт/відновлення; storage error; дві вкладки; клавіатурна навігація; холодний запуск без CDN. Окремо перевірити великі файли та від’ємні коригування.

Поки не варто додавати AI-поради, OCR, командні ролі, мікросервіси чи складний прогнозний рушій: користь від контрольованого імпорту й пояснюваних сум зараз значно конкретніша.
